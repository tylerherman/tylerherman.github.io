Designing Cloud Director in an AI-accelerated pipeline

Designing Cloud Director

At Simpson Strong-tie I took over the designed and prototypeed Cloud Director, a workflow platform for truss manufacturing plants to get it ready for production. The users span office and production floor, from schedulers to plant managers to builders, where a bad design decision costs real operational time and money, not just friction. Everything below is less a list of features and more a record of how I think about speed, quality, and where AI actually helps versus where it needs a human check before it reaches a customer.

Finding the gap: prototype infrastructure

Simpson's internal AI prototyping tool, Abacus, doesn't support cloning or forking prototypes and isn't really setup for collaboration. I proposed a new server setup and app to display all prototypes and allow users to share or if not clone a project to create iterations. This way, users can a/b test features or at least work on shared projects. Also added functionality for commenting so people can provide feedback within the app and pin them to specific areas of the screen.

Splitting time: launch polish and what comes next

Cloud Director had to be ready for a trade show release date, which meant most of my time went into getting the product ready to ship. The design system was already outdated, but replacing it wasn't an option since we were locked into Telerik on the front end, so we were extremely limited in what we could change. On top of that, several dev teams were building in parallel without much review before implementation, so real inconsistencies had piled up across the product by the time launch got close, with limited bandwidth left to fix everything we would have wanted to.

We were also getting pressure from management to get the application looking polished for release. Given the deadline and constraints, I ran several design cleanup passes to catch and document issues, then fixed what I could myself. I got access to the dev environment and wrote CSS directly, since that was the fastest way to close the gap before release.

I outlined the issues with many of our core flows in the app to bring them to attention to the team and propose updates. As you can see here, two separate ways of creating customers, very inconsistent css and style treatments, and lots of areas for improvement. I left most style issues out of the notes as I could fix most of those myself.

Some cleanup to the create project modal and create customer drawer. Far from perfect but what we were able to do with the time crunch to get the app ready for release.

At the same time, launch wasn't the only thing on my plate. I was interviewing beta users for feedback and designing features for the post launch roadmap, so a good part of this period was moving between getting the current product ready to ship and shaping what it needed to become next.

There are many tedious steps from taking in a new project from a customer to getting paid for that work, so I outlined the general process and highlighted places Ai or general automations might come into play to speed things up.

Simplified Pricing Process

One area of the app I was having issues with way pricing and with the project model wanted to address. Currently every design component in a project shows up on the pricing page, whether you want to price it or not. So I designed and prototyped a new workflow where you can add designs to pricing or select designed components directly from the pricing page.

The real reason behind this was user feedback. Components might not be designed at all at the bid stage or very roughly so, so its better for the customer to be able to add a line item bid, then replace the costs when the components have been designed. This redesign makes it super easy to select the components you want to add to a line item. You can either replace the pricing details or if the bid has already been won, just update the cost of the materials.

Project Model Updates

The big post release feature update I was doing research on and designing in Figma and Prototypes for was the project model update. Our initial release only allowed a user to create a Project that contained one set of designs and pricing details that could be sent to production. But there are many ways a customer might want to setup a project. For example you might have multiple bids open at once, each bid could have more than one order created from it, and each order could have change orders created from that.

Additionally, customers have really been asking for ways to create edit custome workflows. So I created a prototype to show this type of behavior. A user would be able to define the content of the table by selecting columns, also be able to select from all tasks for tracking purposes and create custome filters on top of this to create highly specialized views. These view could be shared with others or set as defaults for specific roles in the company. This way everyone can have workflows setup just for their specific tasks.
